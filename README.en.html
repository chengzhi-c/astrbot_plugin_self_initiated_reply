📖 Overview

Yejing (业镜, "Mirror of Karma") lets AstrBot take part in conversations on its own — proactively replying in whitelisted sessions instead of only responding when called by name.

The core idea in four points:

  • After a message arrives, the plugin waits for the conversation to go quiet, then asks a judge model whether it should chime in.
  • Proactive replies are produced by AstrBot's main Agent pipeline, but with tool boundaries tightened by default (they can be relaxed).
  • Direct @Bot mentions, wake words, and commands keep using the normal reply chain — the two paths never interfere with each other.
  • All configuration and runtime state live under AstrBot's data-root directory. Cross-platform group chats are stored as full UMO (Universal Message Object) entries, while bare group IDs remain supported for backwards compatibility.
💡 Where to start: open the Settings Page, then apply the Recommended Configuration to get your first proactive reply running.

🚀 How It Works

The plugin runs as a three-stage pipeline:

  1. Collect — Listens to ordinary messages in whitelisted sessions. Content that explicitly asks to reply, send an image, or find an image is passed through immediately; everything else is handed to the judge model.
  2. Judge — The judge model answers only one question — *reply or not* — and returns strict JSON:
   {"should_reply": true, "reason": "a brief reason"}
  1. Reply — The reply body is generated by AstrBot's main Agent / tool loop, using the full toolchain but with restricted boundaries.

🔒 Tool Boundaries

Proactive replies and @Bot normal replies are two independent paths.

By default, the proactive path disables:

  • third-party plugin tools,
  • Shell / Python execution,
  • file read & write,
  • the browser,
  • cron,
  • skill management,
  • memory writes,
  • and cross-session sending.

When the available tool set cannot be verified, the plugin refuses to run outright (fail closed). The settings page offers an "Allow inheriting plugin tools" option to relax this boundary — but host-level dangerous capabilities (cron, browser / computer use, and file extraction) remain disabled under all circumstances.

🖼️ Image Recognition (Optional)

Off by default. When enabled, text descriptions of the most recent images are attached during the judge or reply-generation phase.

  • Two independent switches. Judge-model vision looks at images when deciding whether to reply; main-model vision looks at images when generating the reply body. The judge phase fires frequently, so enabling only main-model vision saves tokens. Each switch can use its own Provider; within the same Provider, an identical image is described only once and the result is cached in runtime memory per Provider (~50 entries, re-described after a plugin reload/restart or cache eviction), preventing descriptions from leaking across Providers.
  • Stickers can be skipped. QQ OneBot subType=1 stickers are excluded outright without calling Vision.
  • Safe snapshotting. Image snapshots go into the plugin's own image_cache; remote images are frozen in the background so they don't depend on expiring QQ CDN links. Real file formats are validated by magic-number checks, guarding against SSRF and forged paths.
  • Untrusted context only. Descriptions participate in judging solely as untrusted context — they are never written to history or state and can never trigger tools. The cache auto-cleans by expiry and capacity, and the settings page provides a "Clear now" button.

⚙️ Settings Page

A settings page lives inside the plugin detail page, covering:

  • the run switch and whitelist overview;
  • context / delay / silence / cooldown parameters;
  • the judge model (Provider, temperature, timeout, and prompt editing with live preview);
  • batch editing of whitelist UMO entries;
  • and image-cache cleanup.

The UI ships with light and dark themes — light "Boon of Compassion", dark "Court of Judgment" — toggled from the top-right corner and defaulting to your system preference:

Judge model tuning is the most frequently used entry point:

🎯 About the Whitelist

The whitelist has two layers:

  1. AstrBot's global whitelist intercepts first.
  2. Only after passing it does the plugin whitelist decide whether to reply proactively.

/selfreply add adds the *entire group session*. The "Advanced: Whitelist Session IDs" section supports batch editing — you may enter either a full UMO or a bare group ID.

🛠️ Troubleshooting (no proactive replies? click to expand)

Check in order:

  1. Is the session in the proactive-reply whitelist?
  2. Is AstrBot's global whitelist not intercepting it?
  3. Look at /selfreply status.
  4. Check should_reply and reason in the logs.
  5. If the judge model isn't letting it through, tune "judge prompt" and "judge temperature".

After changing plugin code, pages, or metadata, restart AstrBot or reload the plugin to apply the changes.

🔐 Security Notes

⚠️ Security warning: the plugin's settings page and Web API (e.g. /api/plugin/selfreply/config) do not provide independent authentication. Access control relies entirely on the host AstrBot Dashboard's login and permission system.
  • Do not expose AstrBot's web port to untrusted networks.
  • Changes to security-sensitive config (e.g. proactive_inherit_tools, whitelist) are recorded in the plugin INFO logs for later audit.

📌 Summary

Yejing keeps AstrBot helpful without being intrusive: a lightweight judge model decides *when* to speak, the main Agent decides *what* to say, and strict tool boundaries keep every proactive action safe by default. Start from the Settings Page and the Recommended Configuration, then use Commands and Troubleshooting to fine-tune and diagnose. Remember to keep the Dashboard behind trusted access — see Security Notes.
